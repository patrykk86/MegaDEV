# Session knowledge — shells, processes, dispatch

Every line here was paid for by a session that got it wrong.

- **Batch, then reclaim**: issue one `run_commands` array per turn instead of a call per command, and before answering review the shells a turn left behind with a read-only listing. source: operator correction · how: told
- **Reclaim by PID, only what this turn started**: stop a shell only by the exact PID this turn recorded, never by name or age, because that filter selects the operator's own shells; an aborted command keeps its `conhost.exe` alive — one session reached 27 orphan console hosts — so keep foreground waits short and reclaim right after reading. `.vscode/settings.json` sets `terminal.integrated.enablePersistentSessions: false`, so a reload does not resurrect them. source: operator correction · how: told
- **No process outlives its turn, except a reported dispatch**: stop dev servers, watchers and `npx mcp-remote` proxies in the turn that spawned them, unless the operator asked for a standing service, and report their PIDs; a dispatch may outlive the turn only when its PID, log path and result path are reported as it starts and its log read on the next. A server the client declares and spawns (`mega-challenge`) is the client's to end. source: `.clinerules` §6 · how: read
- **Three refusals end the guessing**: when a checkable answer is refused three times and each refusal carries only a count (`missing_tag: 2`), dispatch the whole evidence set to the strongest reasoning tier instead of varying it by hand, because those counts are constraints one model settles in one pass where five hand-guesses did not; mask tokens and ask for strict JSON. source: operator correction, `s03e01/requirements.v1-v6.json` · how: told
- **A dispatch needs output headroom**: a thinking model's cap has to cover reasoning plus answer — 700 tokens came back as 697 reasoning tokens and no text. A reviewer dispatch counts only when its answer is non-empty: 1600, 2600 and 4000 returned zero characters while 900 produced a verdict, so check content before counting a round. On 2026-11-12 the security-tier reviewer (`deepseek/deepseek-v4.1-flash-20261017`) answered a 50-token probe with "OK" yet returned empty content at 400, 900 and 1500 tokens on a 1,379-token code payload, so emptiness is prompt-shape dependent, not a reachability problem — record the round as empty and escalate the review as outstanding instead of swapping in a weaker model or raising the budget again. source: `s03e02/review-round1.md`, `.runs/review-round1.md` · how: ran
- **Fix every finding before the next dispatch**: when a review returns a list, remediate all of it in one pass and re-dispatch once per round, inside the three-round cap `.clinerules` §5 sets, because clearing one item per round spends money on findings the reviewer already gave away. source: operator correction · how: told
- **One decision per message**: attention, not compute, is the bottleneck, so a message to the operator asks for one thing and carries the reason in the same breath. source: `s03e01/LESSON-NOTES.md` · how: read
- **Explore before building in unfamiliar ground**: in an area this session has not touched (OAuth, MCP transport, a new runtime, a remote host), spend one loop surfacing unknowns and leave the decision beside the work, because that knowledge is one prompt away while a wrong build is days from being noticed. source: `s03e01/LESSON-NOTES.md` · how: read
